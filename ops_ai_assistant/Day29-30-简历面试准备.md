## 三、面试高频题 + 标准答案

---

### 🔥 基础概念类

**Q1：什么是 RAG？为什么需要它？**

RAG（检索增强生成）= 让大模型回答问题前先"查资料"，再基于查到的内容回答。

需要它的原因：
1. 大模型知识有截止日期，不知道最新信息
2. 大模型会"幻觉"，不知道的事会编造答案
3. 企业内部知识（运维手册、产品文档）大模型没有训练过

RAG 的本质：把文档向量化存入向量数据库，用户提问时检索最相关的文档片段，
拼入 Prompt 让大模型基于真实资料回答，而不是凭记忆。

---

**Q2：向量数据库的原理是什么？**

把文字转成高维向量（Embedding），语义相近的文字向量距离近。
存储时建立索引（HNSW/IVF等），查询时计算用户问题向量与所有文档向量的相似度，
返回 Top-K 个最相似的文档片段。

常用距离计算：余弦相似度（方向相似）、L2 欧氏距离（绝对距离）。

常用向量数据库：
- Chroma：本地轻量，适合开发测试
- Milvus：生产级，支持十亿级向量
- Pinecone：云服务，开箱即用

---

**Q3：LangChain 的 LCEL 是什么？**

LangChain Expression Language，用 | 符号把各个组件串联成管道：

```python
chain = prompt | llm | StrOutputParser()
result = chain.invoke({"input": "问题"})
```

本质是把 Runnable 接口的对象串联，每个组件的输出作为下一个的输入。
支持流式输出、并行执行、批处理等特性。

---

**Q4：Function Calling / Tool Use 的原理？**

1. 把工具的名称、描述、参数格式传给 LLM
2. LLM 根据用户问题决定是否调用工具，以及调用哪个、传什么参数
3. 代码层执行真实工具函数，获取结果
4. 把工具结果传回 LLM，LLM 基于真实数据生成最终回答

关键：LLM 不执行工具，只负责决策；代码层负责执行。

```python
llm_with_tools = llm.bind_tools(tools)   # LLM 知道有哪些工具
response = llm_with_tools.invoke(messages)
if response.tool_calls:
    # 执行工具
    result = tool_map[tool_name].invoke(args)
```

---

**Q5：RAG 和 Fine-tuning 的区别？什么时候用哪个？**

| 对比项 | RAG | Fine-tuning |
|--------|-----|-------------|
| 成本 | 低，无需训练 | 高，需要 GPU |
| 知识更新 | 实时，改文档即可 | 慢，需重新训练 |
| 可解释性 | 高，能看来源 | 低，黑盒 |
| 适合场景 | 知识问答、文档检索 | 风格迁移、特定能力 |

结论：企业知识库、文档问答用 RAG；
需要改变模型行为/风格/特定领域能力用 Fine-tuning。
90% 的企业场景用 RAG 就够了。

### 🔥 项目深挖类

**Q6：你的 RAG 系统如何保证回答质量？**

三个层面：

1. 检索层：混合检索（向量 + BM25）+ 相似度阈值过滤
   保证检索到的内容与问题高度相关

2. 生成层：Prompt 明确要求"基于上下文回答，不知道说不知道"
   防止大模型在检索内容不足时编造答案

3. 评估层：建立评估体系（忠实度/完整性/清晰度），
   用 LLM 对回答打分，综合得分 4.0/5.0

---

**Q7：你的 Agent 是如何实现的？遇到什么问题？**

实现：
使用 llm.bind_tools 让 LLM 知道工具列表，
手动实现 Agent 循环（最多 6 次工具调用），
LLM 决策 → 执行工具 → 结果传回 → 继续决策，直到 LLM 不再调用工具。

遇到的问题：
1. LangChain 版本升级频繁，create_tool_calling_agent API 多次变更
   → 解决：改用底层 llm.bind_tools + 手动循环，不依赖高层封装

2. 工具描述不清晰导致 LLM 选错工具
   → 解决：优化 @tool 的文档注释，明确说明"什么时候用这个工具"

3. 多工具串联时 Token 消耗大
   → 解决：设置 max_iterations=6，工具结果做截断处理

---

**Q8：RAG 的 chunk size 怎么选？**

原则：太大噪音多检索不准，太小信息不完整。

实践经验：
- 一般场景：500～1000 字符
- 技术文档（有明确段落结构）：按段落切，不硬切
- QA 对话类文档：按问答对切，一问一答为一个 chunk
- overlap（重叠）：50～100 字符，防止关键信息被切断

我的项目：chunk_size=512，overlap=50，
用 RecursiveCharacterTextSplitter 按段落优先切分。

---

**Q9：如何处理大模型的幻觉问题？**

1. RAG：让模型基于检索内容回答，而不是凭记忆
2. Prompt 约束：明确说"不知道就说不知道，不要编造"
3. 相似度阈值：检索结果相似度低于阈值时，直接回答"知识库中无相关内容"
4. 引用来源：回答时附上检索到的原文来源，用户可以核实
5. 评估体系：用忠实度指标检测回答是否忠实于检索内容

---

**Q10：如果知识库很大（10万+文档），性能如何保证？**

1. 向量数据库选型：换 Milvus/Weaviate，支持十亿级向量，有 HNSW 索引
2. 分层检索：先粗排（向量检索 Top100），再精排（重排序模型 Top5）
3. 元数据过滤：先按 category/date 等字段过滤，再向量检索，减少检索范围
4. 缓存：高频问题的检索结果缓存到 Redis，TTL 1小时
5. 异步处理：文档入库异步批处理，不影响查询性能

**Q11：如果让你设计一个企业知识库问答系统，你会怎么做？**

分五层设计：


工程保障：
- 评估体系（忠实度/相关性/正确性）
- 知识库版本管理（文档更新自动重新向量化）
- 用户反馈机制（踩/赞收集，用于持续优化）
- 监控告警（响应时间/召回率/用户满意度）

**Q12：RAG 效果不好时如何排查？**

分三步排查：

第一步：检查检索质量
```python
retriever = index.as_retriever(similarity_top_k=5)
nodes = retriever.retrieve("你的问题")
for n in nodes:
    print(n.score, n.text[:100])
# 看检索到的内容是否包含答案
```

第二步：检查 Prompt
把检索到的内容和问题打印出来，看传给 LLM 的内容是否合理

第三步：检查生成
如果检索内容正确但回答不对，是 Prompt 设计问题或模型能力问题

常见原因及解法：
- 检索不到 → 调大 Top-K，换混合检索，优化 chunk 切分
- 检索到了但回答错 → 优化 Prompt，加强约束
- 回答编造内容 → 加忠实度约束，设置相似度阈值
